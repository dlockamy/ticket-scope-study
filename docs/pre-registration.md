# Follow-up: ticket structure and business process vs repository layout

**Status: screening phase executed 2026-10-29/30; see [the run log](run-log.md) for what ran, the deviations and the results.** The text below is the plan as proposed and is unchanged. The design locks only after the two steps in "Before locking", and the predictions are recorded now, before any data. Builds on [the first study](https://dlockamy.com/posts/2026/11/05/testing-the-monorepo-argument/) (process metrics only; migration and retooling stay out of scope).

## Why

The first study varied the repository layout and held process roughly fixed. It still saw signs that process matters, and it could not size them.

| Observation in the first study | Where |
|---|---|
| Structured and open-ended tickets gave the same correctness and cost, apart from extra exploration (19 vs 12 clones across 7 pairs) | §3.1, §4 |
| A structured ticket that listed only some consumers: the multi-repo developer missed the hidden one, the monorepo developer found it by search | §3.7 |
| Reviewers caught a missing app at 10 and 100 apps only because the list of apps was handed to them; with one app and no list they approved twice | §3.1c |
| A written handoff caught a minor-vs-major version mismatch between two developers | §3.2 |

Most of those cells had one run. The data cannot say whether process matters more, less or the same as layout.

## Question

1. **How much** of the variation in lead time, PR count, rework and missed dependents comes from ticket and process choices, compared with repository layout and with the type of change?
2. **Which practices** reduce misses, rework and lead time, in which layout, and by how much?

## Two starting positions (recorded before data)

* **Position A:** ticket and process quality explain as much or more of the variation in *misses and rework* than layout does, especially in the multi-repo setup.
* **Position B:** layout still dominates the *deterministic* measures (PRs, builds, lead time for crossing changes). Process only moves misses and rework.

Both can be partly right. The study reports which measure each holds for.

## Design

**Layouts:** the existing monorepo and multi-repo fields, same tiers, same pipelines (CI and CD in both).

**Process levers** (generated by script from templates, not written by a model, so ticket text is identical across layouts apart from repository names):

| Lever | Levels |
|---|---|
| L1 Ticket structure | open-ended; structured per-repository tasks; structured plus acceptance checks |
| L2 Dependent information | none; partial list (one consumer missing); complete list; **decoy** list (names a repository that does not consume, and omits one that does); catalog tool `st deps <package>` that is complete; catalog that is **stale** (one entry missing) |
| L3 Work breakdown | single ticket; epic with ordered child tickets |
| L4 Clarification step | none; developer may ask a scripted responder before starting (answers come from a key, with no extra hints) |
| L5 Handoff (team runs only) | none; free messages; required handoff template (release class, version, what changed, who must act) |
| L6 Review input (reviewer runs) | diff only; diff plus consumer list; diff plus checklist |

**Changes** (3 types, each with F = 3 consumers, one of them hidden from the ticket where L2 allows it):
1. Non-breaking addition to the shared library, used by one app.
2. Breaking rename reaching all consumers.
3. Cross-cutting policy change (a new required field every consumer must pass), to test coordination rather than a mechanical edit.

**Cells.** Screening phase: layout (2) × L1 (3) × L2 (6, but only the meaningful combinations with L1) × change type (3), with **5 replicates per cell** (the first study had 1). Team phase: L3 × L5 on 2 developers. Review phase: L6 × layout, repeating the review-burden design with the omission and decoy cases.

**Run order and isolation.** Same as before: snapshot restore before each round, machine held awake, one run at a time per executor pool, because earlier runs showed 4 executors saturate.

**Scoring** is by script, not by judgment: acceptance script on the live bundle; consumers missed; wrong consumers touched (decoy); post-merge breaks; reopened or follow-up PRs; clarifying questions asked; PRs, builds, lines, lead time; messages; tokens and tool calls.

**Second model.** A subset of cells (about a third) repeats with a smaller Claude model as the developer, to see whether the effects belong to one model.

## Analysis (fixed in advance)

* **Variance decomposition** per outcome: share of variance explained by layout, ticket/process levers, change type and their interactions (mixed model with run replicate as the unit). Report effect sizes with intervals, not only significance.
* **Headline comparison:** for each outcome, is the process effect larger than the layout effect? Answer per outcome, not overall.
* **Practice ranking:** a practice is called *recommended for a layout* only if it lowers misses, rework or lead time by at least 20 percent against the open-ended baseline in the cells where it applies, the interval excludes zero, and it holds on the second model.
* **Harm check:** a practice that raises misses or lead time (for example a decoy list that agents trust) is reported as strongly as one that helps.

## Predictions (recorded before data)

1. Misses depend on L2 far more in multi-repo than in monorepo; in the monorepo the effect is near zero.
2. A complete dependent list or catalog removes most of the multi-repo miss gap. A stale catalog brings misses back, because agents trust it.
3. A decoy list costs more than no list (extra wrong work, and the hidden consumer is still missed).
4. Layout still dominates PR count, build count and lead time for the crossing changes (those are set by the topology).
5. Structured per-repository tasks cut multi-repo exploration (fewer clones, less time) and do little in the monorepo.
6. Acceptance checks reduce rework more than task breakdown does.
7. A required handoff template reduces version-class mismatches in team runs.
8. The cross-cutting policy change shows the largest process effect of the three change types.

## Before locking

1. **Outside views first**, as in the first study: survey sources for and against heavy ticket structure and definition-of-ready gates, dependency catalogs and ownership maps, and release-coordination practice, and record them in an evidence note next to monorepo vs multirepo evidence. Add any lever or prediction the survey exposes, so our own view is not the only one tested.
2. **Pilot:** 12 runs to measure run-to-run spread under the new replicate count, check the scripted responder leaks no hints, and fix the sample size. If intervals are too wide at 5 replicates, add 5 more per cell and say so.

## Build list (extends the existing harness)

* Ticket generator with the L1 and L2 levels, and a rubric score for each ticket computed by script (consumers named, acceptance checks present).
* `st deps` catalog tool, with a switch for stale entries.
* Scripted clarification responder, answering only from a key.
* Handoff template check and a version-class mismatch detector.
* Scoring script for misses, decoys, rework and post-merge breaks.

## Cost estimate

About 180 agent runs plus the review phase. The first study averaged roughly 58,000 tokens per developer run (404,000 over 7), so about 10 million tokens, and around 7 to 8 hours of serial wall time at 2 to 3 minutes a run. Estimates only; the pilot replaces them.

## Limits to expect

* Agents, not people: no approval queues, meetings, or ownership disputes. Clarification is counted in rounds, not in waiting time.
* Same model builds the tests and plays the developers (the second-model subset reduces, but does not remove, this).
* Small toy system; the process effects may differ at real scale.
* Tickets come from templates, which makes them cleaner than real ones. Real ticket noise is not tested.

## Out of scope

Migration, retooling, staffing and tooling cost; access control; human reviewer behaviour.
